## 2. 과제 1 — Ctrl+C 를 세 번 눌러야 종료

### 2.1 원본에서 바꾼 것

원본은 플래그 하나(`got_sigint`)를 켜고 첫 SIGINT 에 바로 끝났습니다.
이를 카운터로 바꿔 누른 횟수를 세고, 세 번째에 정리 메시지를 내도록 했습니다.

```c
#define NEED 3
static volatile sig_atomic_t count = 0;

static void handler(int sig)
{
    (void)sig;
    count++;      /* 카운터만 올린다 */
}
```

출력은 전부 `main` 에서 합니다. `count` 는 언제든 바뀔 수 있으므로
`shown` 과 비교하며 따라잡는 방식으로 읽습니다.

```c
while (count < NEED) {
    while (shown < count && shown < NEED) {
        shown++;
        printf("[%d/%d] SIGINT 를 받았습니다. %d 번 남았습니다.\n",
               shown, NEED, NEED - shown);
    }
    if (count < NEED)
        pause();
}
```

### 2.2 실행 결과

```
Ctrl+C 를 3 번 누르면 종료합니다 (PID 277)
[1/3] SIGINT 를 받았습니다. 2 번 남았습니다.
[2/3] SIGINT 를 받았습니다. 1 번 남았습니다.
[3/3] SIGINT 를 받았습니다.

SIGINT 를 3 번 받았습니다. 정리하고 종료합니다.
```

### 2.3 왜 핸들러에서 printf 를 하면 안 되는가

`printf` 는 async-signal-safe 하지 않습니다. `main` 이 `printf` 로 stdout 버퍼를
수정하는 도중에 시그널이 들어와 핸들러가 또 `printf` 를 호출하면, 같은 버퍼를
두 실행 흐름이 동시에 건드립니다. 출력이 깨지거나 버퍼 락에서 데드락이 날 수 있습니다.
POSIX 가 안전하다고 보장하는 것은 `write`, `_exit`, `alarm`, `sigprocmask` 등 제한된 목록뿐입니다.

### 2.4 왜 `volatile sig_atomic_t` 인가

| 키워드 | 빼면 생기는 일 |
|---|---|
| `volatile` | 컴파일러가 "루프 안에서 안 바뀐다" 고 보고 레지스터에 캐싱 → `while (count < NEED)` 가 메모리를 다시 읽지 않아 **무한 루프** |
| `sig_atomic_t` | 읽기/쓰기가 여러 명령으로 쪼개질 수 있음 → 그 사이에 시그널이 끼어들면 **반쯤 쓰인 값**을 읽음 |

PPT 29쪽의 "자주 막히는 지점 — 플래그를 int 로 선언 → 무한 루프" 가 이것입니다.

## 3. 과제 2 — 반복 타이머

### 3.1 원본에서 바꾼 것

원본은 `alarm(3)` 으로 한 번만 울려 입력 타임아웃을 구현했습니다.
여기서는 명령행 인자로 간격과 횟수를 받아 그 횟수만큼 반복하도록 바꿨습니다.

```c
static void on_alarm(int sig)
{
    (void)sig;
    ticks++;

    /* 핵심: alarm 은 한 번만 울리므로 여기서 다시 걸어야 반복된다 */
    if (ticks < repeat)
        alarm((unsigned int)interval);
}
```

`alarm(n)` 은 n초 뒤 SIGALRM 을 **한 번** 보내도록 예약하는 one-shot 타이머입니다.
전달되는 순간 예약이 사라지므로, 반복하려면 매번 다시 걸어야 합니다 (PPT 1.7절).
핸들러에서 `alarm()` 을 부르는 것은 안전합니다 — async-signal-safe 목록에 있습니다.

### 3.2 실행 결과

```
$ ./alarm 2 5
2초 간격으로 5번 울립니다 (PID 284)
[1/5] 알람 (경과 2초)
[2/5] 알람 (경과 4초)
[3/5] 알람 (경과 6초)
[4/5] 알람 (경과 8초)
[5/5] 알람 (경과 10초)

5번 모두 울렸습니다. 종료합니다.
```

경과 시간은 `time()` 으로 실제 측정한 값이라, 재무장이 제대로 동작하는지 바로 확인됩니다.

### 3.3 인자 검증

```
$ ./alarm
사용법: ./alarm <간격초> <반복횟수>
  예) ./alarm 2 5

$ ./alarm 0 5
간격과 반복횟수는 1 이상의 정수여야 합니다.
```

`alarm(0)` 은 "예약 취소" 로 해석되어 타이머가 영영 울리지 않습니다.
그러면 `pause()` 에서 멈춘 채 끝나지 않으므로 미리 걸러냈습니다.

## 4. 과제 3 — 시그널 막아 보기

### 4.1 원본에서 바꾼 것

원본은 5초간 막고 "전달됨 / 아직 대기 중" 만 출력했습니다. 세 가지를 추가했습니다.

1. **막기 전 구간(5초)** 을 둬서 즉시 전달과 비교할 수 있게 함
2. **`sigpending()`** 으로 대기 중인 시그널이 실제로 있는지 눈으로 확인
3. 플래그를 **카운터** 로 바꿔 "여러 번 눌러도 한 번만 전달" 을 증명

```c
sigemptyset(&block);
sigaddset(&block, SIGINT);

sigprocmask(SIG_BLOCK, &block, &old);   /* 막기 — old 에 원래 마스크 저장 */
    /* ... 임계 구역 ... */
sigprocmask(SIG_SETMASK, &old, NULL);   /* 통째로 복원 */
```

### 4.2 왜 `SIG_UNBLOCK` 이 아니라 `SIG_SETMASK` 인가

`SIG_UNBLOCK` 은 **원래부터 막혀 있던 시그널까지 풀어 버립니다.**
이 코드가 호출되기 전에 다른 곳에서 이미 SIGINT 를 막아 뒀다면 그 설정까지 해제됩니다.
`sigprocmask` 의 세 번째 인자에 이전 마스크를 저장해 두었다가 `SIG_SETMASK` 로
통째로 되돌리는 것이 부작용 없는 관용구입니다.

### 4.3 실행 결과 — 막힌 구간에서 Ctrl+C 를 5번 누름

```
[구간 1] 아직 막지 않았습니다. Ctrl+C 를 눌러 보세요. (5초)
  열림... 5
  열림... 4
  >>> 즉시 전달됨 (핸들러 1회째)
  열림... 3
  열림... 2
  열림... 1

[구간 2] 지금부터 SIGINT 를 막습니다. Ctrl+C 를 여러 번 눌러 보세요. (8초)
  막힘... 8  (핸들러 호출 누적 1회)
  막힘... 7  (핸들러 호출 누적 1회)
  막힘... 6  (핸들러 호출 누적 1회)
  막힘... 5  (핸들러 호출 누적 1회)
  막힘... 4  (핸들러 호출 누적 1회)
  막힘... 3  (핸들러 호출 누적 1회)
  막힘... 2  (핸들러 호출 누적 1회)
  막힘... 1  (핸들러 호출 누적 1회)

  마스크를 풀기 직전 점검:
  [해제 전] SIGINT 대기 상태: 대기 중(pending) 있음

[구간 3] 막기를 풉니다.
  [해제 후] SIGINT 대기 상태: 없음
  >>> 대기하던 시그널 전달됨 (핸들러 2회째)

핸들러가 불린 총 횟수: 2회
```

### 4.4 관찰 기록 (과제에서 요구한 내용)

**① 막힌 구간에서 누른 Ctrl+C 는 즉시 처리되지 않았다.**
구간 2 의 8초 동안 `핸들러 호출 누적` 이 `1회` 에서 전혀 변하지 않았습니다.
화면상으로는 아무 일도 일어나지 않은 것처럼 보입니다.

**② 그러나 버려지지도 않았다.**
마스크를 풀기 직전 `sigpending()` 으로 확인하니 `대기 중(pending) 있음` 이 나왔습니다.
커널이 "이 시그널이 도착했었다" 는 사실을 기억하고 있다는 증거입니다.

**③ 복원하는 순간 전달되었다.**
`SIG_SETMASK` 직후 pending 이 `없음` 으로 바뀌고, 핸들러 호출이 1 → 2 로 늘었습니다.

**④ 5번 눌렀지만 핸들러는 1번만 추가 호출되었다.**
표준 시그널의 pending 은 "왔다/안 왔다" **한 비트** 뿐이라 중복이 전부 합쳐집니다 (PPT 1.3절).
이것이 큐에 순서대로 쌓이는 실시간 시그널(`SIGRTMIN`~)과의 결정적 차이이며,
SIGCHLD 핸들러에서 `waitpid` 를 반복 호출해야 하는 이유이기도 합니다.

| 11 | `pause()` 경쟁 조건 언급 없음 | 주석으로 한계와 `sigsuspend()` 대안 명시 | 아래 5.4 참고 |

### 5.4 추가로 확인한 한계 (스스로 발견한 부분)

`while (count < NEED)` 검사와 `pause()` 사이에 시그널이 도착하면 그 깨우기를
놓칠 수 있습니다(lost wakeup). 엄밀하게는 SIGINT 를 블록해 둔 상태에서
`sigsuspend()` 로 "마스크 해제와 대기" 를 원자적으로 수행해야 합니다.

이 실습에서는 한 번 더 누르면 깨어나므로 원본과 같이 `pause()` 를 유지하되,
소스에 주석으로 한계를 명시했습니다.

### 5.5 스스로 설명할 수 있게 학습한 개념

- **async-signal-safe**: 핸들러에서 불러도 안전한 함수의 조건. 재진입 가능하거나
  내부적으로 시그널을 막고 동작해야 함. `printf` 는 버퍼와 락을 쓰므로 해당 없음.
- **마스크와 pending 의 구분**: 마스크는 "지금 받지 않을 목록", pending 은
  "도착했지만 아직 전달되지 않은 것". 별개의 비트셋.
- **표준 vs 실시간 시그널**: 전자는 pending 비트 1개라 중복이 합쳐지고,
  후자는 큐에 쌓여 횟수가 보존됨.
- **`alarm()` 의 one-shot 특성**: 전달 순간 예약 소멸. 프로세스당 하나뿐이라
  새로 부르면 이전 것이 취소됨. 여러 타이머가 필요하면 `timer_create`.

| 증상 | 원인 | 해결 |
